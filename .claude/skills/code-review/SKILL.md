# 代码审查（最严格 · 最标准 · 零容错）

## 立场

本审查以「**不能放过任何一个真问题，也绝不能报出一个假问题**」为目标。宁可多花时间读全上下文，也不凭感觉下结论。每一条结论都必须能回溯到具体代码行，禁止臆测、禁止含糊、禁止报无证据的"可能有 bug"。

审查优先级固定为：**正确性 > 安全 > 并发/资源 > 错误处理 > 性能 > 契约 > 可维护性 > 风格**。风格问题永远排在最后，且归入最低级别。

## 审查范围

先明确审查对象，二选一：

1. **按变更审查**：拿到 diff（`git diff` / `git diff HEAD~1` / 未提交改动 / PR 变更），只审变更行及其受影响的下游调用，不审与本次无关的旧代码（除非旧代码被变更触发而暴露问题）。
2. **按目标审查**：用户指定某文件/函数/类/模块，则审其完整实现 + 全部调用方 + 被调方契约。

无论哪种，**读全文，不只看片段**：拿到一行代码，要向上找它的输入来源，向下找它的输出去向，横跨找所有调用点。

## 审查流程（严格按序执行）

1. **建上下文**：确认语言、运行环境、并发模型、关键依赖、数据的来源与边界。未知的不猜，去查。
2. **通读**：先完整读一遍目标代码，理解意图与数据流，不急着挑错。
3. **逐项核对**：按下文「审查清单」逐条过，每条都用「这个输入会怎样、这个路径会怎样」的方式推演，而不是扫一眼。
4. **验证每条发现**：对每条疑似问题，实际追踪——查定义、查调用方、查文档、必要时跑最小复现。**只有验证成立才写进报告**；验证不了的分成"待确认"并明确标注。
5. **分级 + 排序**：按严重级别排序，同级按影响范围/触发概率排序。
6. **输出报告**：按下方格式输出。

## 严重级别

| 级别 | 含义 | 判定标准 |
|------|------|----------|
| **P0 致命** | 必须修复才能合并 | 崩溃、数据丢失/损坏、资金损失、可利用的安全漏洞、逻辑完全错误 |
| **P1 严重** | 明确缺陷，应尽快修复 | 明确的功能错误、资源泄漏、死锁/数据竞争、潜在安全风险、静默错误 |
| **P2 一般** | 真实但影响受限 | 边界情况处理不当、错误处理缺失、明显性能问题、契约不一致 |
| **P3 轻微** | 代码质量 | 命名不清、重复代码、魔法数字、注释与代码不符、可读性 |
| **P4 建议** | 可选优化 | 更优雅的写法、非必须的抽象、个人偏好 |

> 只有能给出 file:line 证据的才算问题。风格类只能进 P3/P4，严禁把风格拔高成 bug。

## 审查清单

### 1. 正确性（最高优先）

- 边界条件：空值/null、空集合、`0`、负数、`-1`、最大/最小值、越界索引、off-by-one。
- 空指针/空引用解引用：所有可能为 null/None/nil 的访问是否已判空。
- 数值：整数溢出、浮点精度/比较、除零、取模负数、类型截断/隐式窄化、无符号与有符号混用。
- 循环与递归：终止条件是否可达、是否可能死循环/无限递归、循环变量是否被误改。
- 状态与分支：`if/else` 是否覆盖所有分支、`switch` 是否漏 `default`、布尔条件是否写反（`&&`/`||`/`!` 误用）。
- 返回值与错误码：所有函数返回值/错误码是否被检查、被忽略的返回值是否会改变程序走向。
- 字符串与编码：索引/切片是否按字符还是字节、编码是否一致、格式化参数是否匹配占位符、拼接是否可注入。
- 时间与时区：时区是否统一、`>`/`>=` 边界、时间戳单位（秒/毫秒）是否混淆。

### 2. 安全

- 注入：SQL 注入（拼接 vs 参数化）、命令注入、XSS（未转义输出）、路径穿越、LDAP/日志注入。
- 敏感信息：密钥/密码/token/私钥/证书是否硬编码、是否写进日志、是否提交进仓库。
- 认证与授权：是否缺失认证、是否可越权（IDOR）、权限校验是否只在前端、会话/token 是否校验失效。
- 数据安全：反序列化不可信数据、加密算法是否过时（MD5/SHA1/3DES）、随机数是否可预测（未用加密安全随机源）、明文存储。
- 依赖：引入的第三方依赖是否有已知漏洞、是否锁定版本、是否引入不必要的大依赖。

### 3. 并发与资源

- 资源释放：内存、文件句柄、数据库连接、网络连接、锁、信号量是否保证释放（RAII / try-with-resources / defer / context）。
- 泄漏路径：异常路径、提前 return、panic/异常分支是否也释放了资源。
- 数据竞争：共享可变状态是否加锁/原子操作，读写是否在正确锁保护下，是否存在 check-then-act 竞态。
- 死锁与活锁：多锁获取顺序是否一致、是否在持锁时做耗时/阻塞操作。
- 原子性：多步操作是否应包在事务/临界区内，失败是否回滚、是否留下半成品状态。
- 生命周期：对象/goroutine/线程/回调的生命周期是否清晰，是否存在 use-after-free / 悬垂引用 / 泄漏的 goroutine。

### 4. 错误处理

- 吞异常：空 `catch` / 裸 `except` / 忽略 error 是否吞掉了关键错误。
- 错误传播：是否丢失了原始错误上下文（只抛 `new Exception` 不带 cause）、错误信息是否误导。
- 失败一致性：失败后状态是否与预期一致（是否已改了一半就退出）、是否可安全重试。
- 输入校验：外部输入（用户、网络、文件、API）是否在入口处校验，非法输入是否被明确拒绝而非静默接受。
- 降级与超时：网络/外部调用是否有超时、重试、熔断、降级策略。

### 5. 性能

- 复杂度：是否存在不必要的 O(n²) 及以上、循环内重复查询/计算/分配。
- N+1 查询：循环内逐条查询数据库/远程接口。
- 内存：大对象无谓拷贝、循环内拼接字符串、未限制大小的缓存/集合、过早加载大结果集。
- 锁与阻塞：锁粒度过大、同步操作本可异步、不必要的全局串行化。
- 只报「可证实的」性能问题：复杂度可算、路径可测才算，不报"可能慢"。

### 6. 接口与契约

- 契约一致：函数名/注释/文档描述与实际行为是否一致、参数语义是否清晰。
- 向后兼容：公共 API 是否破坏签名、返回结构、语义。
- 返回值约定：null/空/错误如何约定、调用方是否知晓并处理。
- 幂等与副作用：操作是否有隐藏副作用、是否应幂等。

### 7. 可维护性

- 命名：变量/函数/类型名是否名副其实、是否用 `data`/`tmp`/`x1` 等无意义名。
- 重复：是否存在可提取的重复代码（违反 DRY）。
- 结构：函数/类是否职责过多、是否过长、是否混合多个抽象层级。
- 死代码：不可达代码、未使用的变量/参数/导入、注释掉的代码。
- 魔法数字：无解释的字面量是否应提取为具名常量。
- 注释：注释是否与代码不符、是否在解释「为什么」而非复述「是什么」。

### 8. 测试

- 覆盖：是否缺边界用例、异常路径、安全用例、并发用例、回归用例。
- 断言质量：断言是否真验证了行为（还是只断言不抛异常/只断言非 null）。
- 隔离性：测试是否相互依赖、依赖顺序、依赖外部真实服务/时间/随机数导致不稳定。
- 可维护性：测试是否可读、是否一测一意图。

## 输出格式

每条发现用统一结构，按严重级别从 P0 到 P4 分组，组内按影响排序：

```
[P0 致命] src/user.py:42  除零崩溃
  问题：count 可能为 0，未判空直接做除法。
  原因：count 来自外部输入，入口处无校验。
  影响：count=0 时抛出 ZeroDivisionError，服务崩溃。
  修复：在除法前校验 count > 0，或捕获并返回业务错误。

[P3 轻微] src/user.py:17  命名不清
  ...
```

报告结尾附一段总评：

```
总评：共 N 条（P0 x 条 / P1 x 条 / P2 x 条 / P3 x 条 / P4 x 条）。
      必须修复：…（P0/P1）
      建议修复：…（P2）
      可选：…（P3/P4）
      （若 0 条问题，明确说"未发现问题"，不硬凑。）
```

## 铁律（禁止事项）

1. **禁止假阳性**：每条 P0/P1/P2 结论必须经实际追踪验证（查定义、查调用方、必要时复现）。验证不了就降级为"待确认"或直接不提，绝不报一个不成立的 bug。
2. **禁止无证据结论**：必须有 `file:line`。写不出位置说明还没查清，回去查。
3. **禁止臆测运行结果**：能实际运行就运行验证；不能运行的，明确标注「未验证，基于静态分析」，不把推测写成事实。
4. **禁止拔高风格**：命名、排版类只能进 P3/P4，不得伪装成正确性/安全问题。
5. **禁止遗漏**：按清单逐条过，不挑好审的审。数据来源、异常路径、并发、资源释放这四类最易漏，重点盯。
6. **禁止为凑数而报**：没有真问题就如实说"未发现问题"，不为了显得严格而鸡蛋里挑骨头。
7. **区分确定与待确认**：确定的写级别，拿不准的单独列「待确认」，二者不混。
